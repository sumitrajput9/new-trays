# PrintTrays

A local print-bridge system: a background app (system tray, Node.js + Electron) that gives any web page secure access to OS printers, thermal/label printers, and USB/serial devices over a signed local WebSocket connection — plus a client SDK and marketing/demo site.

This is an original codebase and product (name: **PrintTrays**). It does not reuse code, certificates, or branding from any existing print-bridge product.

## Layout

```
/server        Node.js + TypeScript + Electron background bridge app (tray icon, WSS server, printer/serial/USB integration)
/client-sdk    Browser JS/TS SDK websites include to talk to the bridge
/installers    Per-OS packaging config + post-install scripts (cert trust, autostart)
/website       Next.js (TSX) marketing/download/demo/docs site
```

## Stack

- **Server / tray app:** Node.js + TypeScript, packaged with **Electron** (gives us a real system tray, native printer enumeration via `webContents.getPrintersAsync()`, and one codebase for Windows/macOS/Linux). WebSocket server via `ws`, TLS via Node's `https` module with a self-signed cert generated by `node-forge`. Serial I/O via `serialport`, USB/HID via `usb` + `node-hid`.
- **Client SDK:** TypeScript compiled to a native ES module — drops into any page with `<script type="module">`, no bundler required.
- **Website:** Next.js (TSX / App Router).

For deploying this to teammates and wiring it into an existing web app (e.g. Qrinto) for silent printing, see [`TEAM-GUIDE.md`](TEAM-GUIDE.md).

## Getting started (development)

```bash
npm install          # installs all three workspaces (server, client-sdk, website)

npm run server:build # compile the Electron app's TypeScript
npm run server:dev   # run it locally — a tray icon should appear, bridge listens on wss://127.0.0.1:8181

npm run sdk:build    # compile client-sdk to client-sdk/dist

npm run website:dev  # http://localhost:3000 — landing, /download, /demo, /docs
```

To try the live demo end-to-end: run `server:dev`, then `website:dev`, then open `/demo` — it connects to your locally running bridge and lets you send a real test print.

> **First-run certificate warning:** until you've run an installer (which imports the local CA into your OS trust store — see `/installers`), your browser will show a self-signed certificate warning the first time a page connects to `wss://127.0.0.1:8181`. This is expected in dev.

## Building installers

```bash
npm run server:dist:win     # NSIS .exe  -> installers/out/
npm run server:dist:mac     # .pkg + .dmg -> installers/out/
npm run server:dist:linux   # .AppImage + .deb -> installers/out/
```

Packaging is `electron-builder`, configured in [`server/package.json`](server/package.json). See [`installers/README.md`](installers/README.md) for what each platform's post-install step does (certificate trust import, autostart registration) and — importantly — **what you still need to supply yourself**: real icon artwork, a Windows code-signing certificate, and an Apple Developer ID + notarization credentials. None of those can be generated by this scaffold; they involve purchasing a cert / enrolling in Apple's program and are out of scope for generated source code.

## Deploying the website

`website/` is a standard Next.js app — `npm run website:build && npm run start --workspace website`, or deploy to any Next.js-compatible host. Before going live:

1. Host the real installer binaries somewhere and update the links in [`website/app/download/page.tsx`](website/app/download/page.tsx).
2. Replace [`website/public/printtrays.js`](website/public/printtrays.js) with the actual built output of `client-sdk` (or serve it from a CDN) rather than the hand-copied demo version.

## How the pieces fit together

1. `server` runs in the background, generates a self-signed local CA + TLS cert on first launch (`certManager.ts`), and a separate RSA keypair used only to sign outgoing WebSocket messages (`signing.ts`).
2. A web page loads `client-sdk`, calls `connect()`, which opens `wss://127.0.0.1:8181` and pins the bridge's signing public key (trust-on-first-use) in `localStorage`.
3. Every response from the bridge is verified against that pinned key with WebCrypto before the SDK resolves a promise — this is PrintTrays's equivalent of QZ Tray's message-signing trust layer, implemented independently.
4. `print` / `rawWrite` / `listDevices` requests are dispatched in `wsServer.ts` to `printerService.ts` (OS print spooler via Electron), `rawPrint.ts` (direct TCP/serial byte writes for thermal/label printers), `serialService.ts`, and `usbHidService.ts`.
5. The tray icon (`tray.ts`) shows live connection count and exposes Open / Restart / Quit / About.

## Known scope limits of this scaffold

- **Native module builds:** `serialport`, `usb`, and `node-hid` compile native addons per platform. `electron-builder` handles this via its native rebuild step, but you'll need each target OS (or CI runners for each) to actually produce working binaries — you can't cross-compile these from a single machine.
- **Raw printing to standard OS printers on Windows** goes through a `copy /b` to `\\localhost\<share>` as a pragmatic workaround, since raw ESC/POS/ZPL passthrough isn't part of Node's/Electron's built-in print API — real production use should call the WinSpool API via a native addon (e.g. `printer` npm package or a custom N-API module) for reliability across driver types.
- **USB HID raw device I/O** (`usbHidService.ts`) enumerates and writes to HID devices; talking to a printer over raw (non-HID) USB bulk endpoints needs interface claiming/kernel-driver detachment that's highly device-specific and is left as a documented extension point rather than guessed at generically.
- No installer binaries, certificates, or hosting are actually produced here — see [`installers/README.md`](installers/README.md) for exactly what's left to supply.
